# Архітектура GhostTalk

GhostTalk — це PoC вебзастосунку для проведення структурованих анонімних фасилітаційних сесій: збір ідей, голосування, модерація, підсумок і, опційно, відеокімната.

## Загальна схема

```text
Браузер (React + Vite)
        │ HTTP / SSE
        ▼
Nginx (у Docker; проксі /api)
        │
        ▼
Go Backend (net/http)
 ├── PostgreSQL — сесії, учасники, картки, голоси, підсумки, аудит
 ├── SSE Hub — миттєві події для відкритих сторінок
 ├── Whisper — розпізнавання мовлення
 ├── Piper TTS — синтез мовлення
 ├── Anonymous-audio worker — стан анонімного аудіорежиму
 └── LiveKit — відео/аудіокімнати та JWT-токени доступу
```

У production Nginx є єдиною публічно доступною точкою входу на портах `80/443`; backend і PostgreSQL залишаються у внутрішній Docker-мережі. Локально frontend доступний на `13000`, API — на `18080`, БД — на `55432`.

## Складові

- `frontend/` — React-застосунок із React Router, Tailwind і локалізацією українською/англійською.
- `backend/` — Go REST API на стандартному `net/http`. Тут зосереджені правила доступу, валідація, робота з БД, SSE та інтеграції.
- `db/migrations/001_init.sql` — схема PostgreSQL.
- `tts/` — FastAPI-сервіс поверх Piper, який повертає WAV для заданого тексту й голосу.
- `anonymous-audio-worker/` — FastAPI worker готовності та runtime-статусу анонімного аудіорежиму.
- `media-worker/` — consent-gated LiveKit audio subscriber. Він збирає фінальні аудіофрази в RAM, надсилає їх у STT через backend, записує лише фінальні PII-redacted transcript segments і публікує тільки processed synthetic/masked track. Raw media не зберігається й не перепубліковується.
- LiveKit — окремий real-time медіасервер для відео та аудіо, може бути локальним або зовнішнім.
- Docker Compose — збирає та запускає усі сервіси.

## Дані в PostgreSQL

Основні сутності:

- `sessions` — сесія: код приєднання, методологія, відеокімната, ліміт учасників, стан голосування та завершення.
- `participants` — анонімні учасники, прив’язані до випадкових токенів із терміном дії.
- `cards` — картки з текстом, категорією, кількістю голосів і ознакою приховування.
- `votes` — голоси; унікальність `(card_id, participant_id)` не дає проголосувати за одну картку двічі.
- `summaries` — фінальний Markdown-підсумок, згруповані думки, ризики/питання й action items.
- `audit_events` — журнал подій та дій.
- `voice_templates` і `participant_anonymous_audio` — шаблони голосів та налаштування анонімного аудіорежиму.

## Як проходить сесія

1. Фасилітатор створює сесію через `POST /api/sessions`.
   - Обирає методологію: `brainwriting`, `swot`, `start_stop_continue` або `anonymous_qa`.
   - Backend створює короткий код, наприклад `ABC123`, назву LiveKit-кімнати та токен фасилітатора.
   - Токен також встановлюється у cookie; саме він надає права модератора.

2. Учасник відкриває `/session/:code`.
   - За потреби проходить captcha або вводить секрет приєднання.
   - Backend створює анонімний participant token, зберігає його в cookie й не вимагає акаунта.

3. Учасник надсилає картку.
   - Клієнт викликає `POST /api/sessions/:code/cards`.
   - Backend перевіряє токен, методологію та категорію, записує картку в БД.
   - Після зміни backend публікує SSE-подію для всіх, хто дивиться цю сесію.

4. Учасники голосують.
   - Запит іде на `POST /api/cards/:id/vote`.
   - Обмеження дублювання забезпечується і кодом, і унікальним обмеженням у БД.
   - Стан голосування може вимикати фасилітатор.

5. Фасилітатор працює на `/facilitator/:code`.
   - Може приховувати картки, переносити їх між категоріями, відкривати/закривати голосування, завершувати сесію і зберігати підсумок.
   - Аудит доступний на `/facilitator/:code/audit`.

6. Підсумок відображається на `/summary/:code`.
   - Дані беруться з `summaries` та карток із найбільшою кількістю голосів.
   - Передбачено Markdown-експорт.

## Realtime-механізм

Для синхронізації карток, голосів, стану сесії та анонімного аудіо використовується Server-Sent Events:

```text
Frontend відкриває EventSource
/api/sessions/:code/events

Backend змінює дані → Hub.Broadcast(code, event)
                         ↓
         усі підписані вкладки оновлюють UI
```

Це односторонній канал server → browser. Дії користувача, навпаки, виконуються звичайними HTTP-запитами.

Важливе обмеження: SSE Hub зберігається в пам’яті одного backend-процесу. Тому поточна реалізація розрахована на один інстанс backend; для горизонтального масштабування знадобиться спільний broker, наприклад Redis Pub/Sub.

## Голос і відео

- Голосове введення: frontend записує аудіо, відправляє його на `/api/transcribe`, а backend проксіює запит у Faster Whisper.
- Озвучення: frontend викликає `/api/synthesize`, backend передає текст до Piper TTS.
- Відеокімната: сторінка `/video/:role/:code` запитує JWT у backend (`/video-token`) і підключається до LiveKit.
- Анонімний аудіорежим зберігає обраний voice template, мову, PII-redaction/fallback-параметри і транслює стан через SSE. У dual topology `media-worker` consent-gated підписується на private input room, записує лише redacted transcript segments і публікує processed synthetic/masked track у public room. Latency/privacy review та benchmark для production залишаються обов’язковими.

## Інтерфейс: реальні та демонстраційні сторінки

Є два шари UI:

- Реальний потік: `/session/:code`, `/facilitator/:code`, `/summary/:code`, `/video/...` — працює з backend API.
- Product/demo екрани: `/dashboard`, `/live/demo`, `/participant/demo`, `/results/demo`, `/settings` — це переважно презентаційний workspace; не всі вони під’єднані до реальних даних сесії.

## Безпека й доступ

- Анонімність учасника реалізована токеном, не логіном.
- Токени фасилітатора й учасника мають TTL: за замовчуванням 30 і 7 днів відповідно.
- Є rate limiting для частини операцій, валідація вхідних даних, CORS allowlist, cookie-токени та аудит.
- У production API не публікується напряму; зовнішній доступ має йти через Nginx/HTTPS.
- `.env` містить інфраструктурні секрети й не повинен потрапляти в Git.
